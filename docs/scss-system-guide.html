0. How To Read This Handbook

The goal of this guide is not to make you memorise Sass syntax. It is to help you make good architecture decisions inside this Shopify theme. Architecture means: where does this code go, and why. Most bugs in big SCSS codebases happen because somebody put the right code in the wrong folder.

Kitchen analogy. A kitchen has a pantry (raw ingredients), a recipe book (instructions), and finished dishes on a plate. SCSS works the same way: the abstracts/ folder is the pantry (tokens, mixins, functions). The components/, sections/, and utilities/ folders are recipes that combine ingredients into finished UI. The compiled main.css file is the plate the browser eats. If you put a fork in the pantry, you can still cook — but the next chef will be confused.
1

Remember the browser only reads compiled CSS

The browser does not understand @mixin, @use, or $variables. Sass is a build-time language. It compiles to plain CSS and that CSS is what the storefront actually serves. Whenever you change SCSS, ask: "what will the compiled CSS look like?"

2

Choose the owner before you write

Before you write a single line, decide which folder owns it: abstracts/, base/, components/, layout/, sections/, templates/, or utilities/. Each folder has one job. Section 3 explains them.

3

Reuse only when the pattern is real

A pattern is "real" when the same group of declarations shows up in three or more places and means the same thing. Two repetitions might be coincidence. One repetition is never enough to justify a helper. A premature helper is worse than a copy-paste.

4

Verify by reading the compiled CSS

After you change SCSS, run the build (npm run build:css) and look at the output diff. If you were doing a "source-only refactor" (just cleaning up), the compiled CSS should be unchanged. If the output changed, something more than cleanup happened — and that means visual QA is needed.

Beginner

1. Fundamentals: CSS, Sass, SCSS

Three words people mix up. They are not three competing technologies — they are three layers of one stack.

CSS

What the browser reads. Plain text rules like .title { color: red; }. No variables, no functions, no @use. In this theme the final CSS lives in assets/main.css (readable) and assets/main.min.css (minified, served to shoppers).

Sass

A language that compiles into CSS. Sass adds tools that CSS cannot do on its own: variables, functions, mixins, loops, maps (lookup tables), and modules. You write Sass; a build tool turns it into CSS.

SCSS

The flavour of Sass we use. Sass has two syntaxes. The original (.sass) uses indentation. The newer SCSS (.scss) looks exactly like CSS but with extra superpowers. Every .scss file in styles/ is SCSS. Any valid CSS is also valid SCSS, so you can paste plain CSS straight in.

Why this matters

Reviewers will say things like "the browser cannot see your mixin" or "this changes compiled output". They mean: the only thing that ships to the shopper is the compiled CSS. Sass features only help us write that CSS more cleanly.

Bakery analogy. Sass is the recipe written in your notebook. CSS is the cake on the counter. The customer eats cake, not your notebook. A reviewer looking at "compiled CSS" is looking at the cake.
source.scss
$title-color: #161616;

.product-card__title {
  margin: 0;
  color: $title-color;
  font-size: 18px;
  line-height: 1.3;
}
compiled.css
.product-card__title {
  margin: 0;
  color: #161616;
  font-size: 18px;
  line-height: 1.3;
}

Line by line

  1. $title-color: #161616; — declares a Sass variable. Variables start with a dollar sign. They exist only at build time. The compiled CSS contains the value #161616 directly; the name $title-color is gone.
  2. .product-card__title — a normal CSS selector. The double underscore is just a naming convention (BEM: Block__Element). Sass does not care about it.
  3. margin: 0; — a normal CSS declaration. Sass passes it through unchanged.
  4. color: $title-color; — Sass replaces $title-color with its value during compile. The browser sees color: #161616.
  5. Everything else is plain CSS.

2. Modules: How Files Talk To Each Other

A Shopify theme has many .scss files. They share variables and mixins by importing each other. Sass has three keywords for this: @use, @forward, and @include. These three words confuse almost every beginner. Read this section slowly.

Library analogy. Think of each .scss file as a book. @use is "checking a book out" — your file can now read it. @forward is "putting a book on the front-desk shelf" — the building entrance now also offers it. @include is "photocopying a page" — the mixin's lines are copied into your stylesheet at that spot.

@use — load another file

sections/_main-product.scss
@use "../abstracts" as *;
@use "../components/form-controls";

Line by line

  1. @use — the keyword that loads another Sass module. "Module" just means another .scss file (the underscore at the start of the filename is dropped when importing; you write "abstracts" not "_index").
  2. "../abstracts" — a path. Two dots mean "go up one folder". So from sections/_main-product.scss, this points at styles/abstracts/_index.scss. When you import a folder, Sass automatically loads its _index.scss.
  3. as * — the namespace. The star means "no namespace, dump everything into the global scope of this file". After this line, you can call spacing(16) and @include stack(...) directly. This is OK for the foundation (abstracts/) because there is only one of it.
  4. @use "../components/form-controls"; — no as *. The default namespace is the filename without the underscore. So mixins from this file are reached as form-controls.control-frame(...). Keeping the namespace makes the source readable: a reviewer can instantly see which API the mixin belongs to.
Rule of thumb. Use @use "../abstracts" as *; only for the foundation (tokens, breakpoints, spacing, mixins). For component APIs like form-controls, product-price, quantity, keep the namespace. The call site becomes self-documenting.

@forward — re-export from a folder entry point

styles/abstracts/_index.scss
@forward '_config.variables';
@forward '_config.breakpoints';
@forward '_config.font-variables';
@forward '_tools.color-palette';
@forward 'tokens';
@forward 'mixins';

Line by line

  1. Each line says: "when somebody @uses this folder, also give them what is inside this partial."
  2. @forward is different from @use. @use means "I want to use these things here". @forward means "pass these things through to whoever loads me, but I am not using them in this file myself."
  3. This is why @use "../abstracts" as * in a section file gives you access to all the spacing functions, breakpoint mixins, tokens, and helper mixins in one go. The _index.scss file forwarded them.
Receptionist analogy. @forward is the receptionist at the front desk. People arriving at the building (other files) ask for tools by name; the receptionist hands them over without using them herself. @use is the worker who actually picks up the tool to do a job.

@include — run a mixin and emit CSS

source.scss
@use "../abstracts" as *;

.newsletter {
  @include stack(spacing(16));
}
compiled.css
.newsletter {
  display: flex;
  flex-direction: column;
  align-items: stretch;
  gap: 16px;
}

Line by line

  1. @include stack(spacing(16)) — calls the stack mixin with one argument, spacing(16).
  2. spacing(16) is a function call. It looks up the key 16 in the spacing map and returns 16px. (Section 7 explains functions.)
  3. The stack mixin then emits four CSS declarations: display: flex, flex-direction: column, align-items: stretch, and gap: 16px. Those declarations land inside .newsletter in the compiled CSS.
  4. Important: every time you @include a mixin, those declarations are copied into the output. Two calls = two copies. Keep mixins small.

3. The Folder System: Seven Buckets, One Job Each

This theme's styles/ directory has seven sub-folders. Each one has a single job. If you can name the job, you can decide where new code belongs.

Folder Its one job Examples in this theme Emits CSS on its own?
abstracts/ The "pantry". Tokens, functions, breakpoints, and reusable mixins that do not emit CSS by themselves. _tokens.scss, _mixins.scss, _spacing.scss, _typography.scss, _config.breakpoints.scss No.
base/ Element-level resets and defaults that apply to bare HTML (body, a, img). _index.scss Yes.
layout/ Large structural pieces present on most pages: header, footer, the main grid. _header.scss, _footer.scss Yes.
components/ Reusable styling primitives (mixins) for UI patterns that several sections share: buttons, form fields, price displays, quantity controls. _button.scss, _form-controls.scss, _product-price.scss, _quantity.scss Most files in here are mixins only — no CSS until included.
sections/ Styles for one specific Shopify section. _main-product.scss, _featured-product.scss Yes.
templates/ Styles tied to one Shopify template page (cart page, checkout, etc.). _cart.scss Yes.
utilities/ Tiny single-purpose classes that Liquid markup applies directly: .sr-only, .truncate, .text-center, .stack-16. _visibility.scss, _text.scss, _flex.scss, _spacing.scss, _layout.scss, _color.scss Yes.
Wardrobe analogy. abstracts/ is the rack of fabrics and buttons (raw materials). components/ is the rack of finished sleeves and collars (sub-assemblies). sections/ and templates/ are the finished outfits hung up for specific days. utilities/ is the drawer of socks, belts, and pins — small accessories you can attach to any outfit. base/ and layout/ are the fitting room itself.

The entry point

styles/main.scss
@charset 'UTF-8';

@use 'abstracts' as *;
@use 'base';
@use 'layout';
@use 'components';
@use 'sections';
@use 'templates';
@use 'utilities';

Line by line

  1. @charset 'UTF-8'; — declares the character set. Standard at the top of CSS/SCSS files; it lets the build emit a matching @charset in the output.
  2. @use 'abstracts' as *; — load the foundation. The star means: the tokens, functions, breakpoint helpers, and base mixins are available globally inside main.scss. (Side note: each sub-file still needs its own @use "../abstracts" as *; at the top — Sass module scope is per-file.)
  3. @use 'base'; through @use 'utilities'; — load each layer in order. The order is meaningful: each later layer's selectors appear later in the compiled CSS. Later selectors of equal specificity override earlier ones. That is why utilities are last — utility classes are expected to win over component defaults.
The folders are loaded in the order: abstracts → base → layout → components → sections → templates → utilities. If two selectors have the same specificity, the one in the later folder wins in the cascade. Utilities are last on purpose.

4. Where Does This Code Go? Decision Games

The single most important question in this codebase. Practise it now with three real scenarios. The rule is: put code where it is owned. Ownership = "if this breaks, who is responsible?"

5. Tokens: Naming Decisions, Not Numbers

A token is a Sass variable that gives a name to a design decision. The name should describe the role (what it means), not the value (what number it currently is). Good tokens make the codebase easier to change later.

Light-switch analogy. "Living room ceiling light" is a good name. "The white switch" is a bad name. If you ever repaint the wall, the white switch is now a green switch — the name lies. A token named by role ($control-height-product) stays meaningful even if the number changes. A token named $px48 would lie the moment you change it to 50px.

Real tokens in this theme

styles/abstracts/_tokens.scss
$transition-duration-fast: 0.2s !default;
$transition-duration-base: 0.3s !default;
$transition-duration-slow: 0.4s !default;

$focus-ring-width: 2px !default;
$focus-ring-offset: 2px !default;
$focus-ring-color: currentColor !default;

$radius-sm: 4px !default;
$radius-md: 8px !default;
$radius-lg: 12px !default;
$radius-control: 8px !default;
$radius-pill: 80px !default;
$radius-round: 9999px !default;

$control-height-sm: 40px !default;
$control-height-md: 48px !default;
$control-height-product: 62px !default;

Line by line

  1. $transition-duration-fast: 0.2s !default; — declares a Sass variable. The dollar sign means it is a variable. The value is 0.2s.
  2. !default — a Sass flag that means "only set this value if it has not been set yet". This lets another file (loaded before this one) override the token without editing this file. It is the safe way to publish design tokens.
  3. Notice the names: fast, base, slow — not 200ms. Roles, not values.
  4. $control-height-product: 62px — the product page uses a chunkier control height than other forms. The token name says where and why, not just the number.

When a number deserves a token

Good candidate

A value appears in two or more places and means the same thing (a "control height", a "focus ring width", a "fast transition"). Naming it once lets you change all the call sites with one edit.

Bad candidate

A one-off pixel value used inside one section. Wrapping it in a token adds a layer of indirection that future readers have to chase, for no benefit.

Even better than a token

When the value is part of a system (spacing scale, font size scale, breakpoint scale), use a function like spacing(16) or font-size(24) instead. Functions validate the key and fail loudly if you ask for one that does not exist.

Where they live

Numerical tokens in abstracts/_tokens.scss. Colour tokens in abstracts/_tools.color-palette.scss. Typography scale in abstracts/_typography.scss. Spacing scale in abstracts/_spacing.scss.

6. Mixins: Reusable Blocks Of Declarations

A mixin is a chunk of CSS declarations you give a name. When you @include it, Sass copies those declarations into the selector at the include site. Mixins do not return a value — they emit lines of CSS.

Stamp analogy. A mixin is a rubber stamp. @include presses the stamp onto the page. Each press leaves another copy of the ink. If the stamp has 12 lines of text and you press it 20 times, you have used a lot of ink — 240 lines of CSS in the compiled file. Section 12 has a do/don't about this.

The most-used mixins in this theme

Mixin Lives in What it emits When to reach for it
stack($gap, $align) _mixins.scss A vertical flex column with gap. A list of items stacked top-to-bottom with consistent spacing.
cluster($gap, $justify, $align, $wrap) _mixins.scss A horizontal, wrapping flex row. Action rows, tag chips, anything that flows horizontally and wraps on small screens.
line-clamp($lines) _mixins.scss Webkit line-clamp truncation for multi-line text. Cap a description at N lines with an ellipsis.
text-truncate _mixins.scss Single-line ellipsis (overflow + nowrap). Truncate one line of text in a fixed-width container.
focus-ring / focus-ring-visible _mixins.scss Outline-based focus ring; -visible also wires up :focus-visible. Any interactive element. Use focus-ring-visible on buttons/links.
absolute-fill _mixins.scss Position absolute, top/right/bottom/left = 0. An overlay element that covers its positioned parent.
inline-center / flex-center _mixins.scss Inline-flex (or flex) with both axes centered. Icon buttons, badges, small centred chips.
transition-config($props, $duration, $easing) _mixins.scss The three transition properties, using token defaults. Any hover/state transition; defaults make the timing consistent across the theme.
card-surface($bg, $radius, $padding) _mixins.scss Background + border-radius + optional padding. A boxed card container.
visually-hidden / visually-hidden-focusable _mixins.scss Standard accessible-hidden pattern. Powers the .sr-only utility; use directly if you do not want the class.
section-space($padding-y, $padding-x) _mixins.scss Vertical (and optional horizontal) padding. Set a section's outer spacing.
container-inline($max-width, $padding-x) _mixins.scss Centered container with max-width and inline padding. Wrap content into a readable width.

Reading a mixin definition

styles/abstracts/_mixins.scss (excerpt)
@mixin cluster($gap, $justify: flex-start, $align: center, $wrap: wrap) {
  display: flex;
  flex-wrap: $wrap;
  align-items: $align;
  justify-content: $justify;
  gap: $gap;
}

Line by line

  1. @mixin cluster(...) — declares a mixin named cluster. The parentheses list its arguments.
  2. $gap — required argument. No default; the caller must supply it.
  3. $justify: flex-start — optional argument with a default. If the caller omits it, the mixin uses flex-start.
  4. $align: center, $wrap: wrap — more optional defaults.
  5. The body is five CSS declarations. The $variables get replaced by the caller's values during compile.

Reading the call site

layout/_header.scss
@use "../abstracts" as *;

.header__row {
  @include cluster(spacing(8), space-between, flex-start, nowrap);
}
compiled.css
.header__row {
  display: flex;
  flex-wrap: nowrap;
  align-items: flex-start;
  justify-content: space-between;
  gap: 8px;
}

Line by line

  1. @include cluster(...) — runs the mixin. The arguments are passed in order: $gap = spacing(8), $justify = space-between, $align = flex-start, $wrap = nowrap.
  2. spacing(8) resolves to 8px (see Section 7).
  3. The compiled CSS shows the mixin's five declarations stamped inside .header__row.
Named arguments. When a mixin has many parameters, prefer named arguments at the call site: @include cluster($gap: spacing(8), $wrap: nowrap). It reads better and you only have to supply the ones you care about.

7. Functions: Lookups That Return A Value

A function in Sass takes inputs and returns a single value. Unlike mixins, functions do not emit declarations — they are used inside a declaration where you need a value.

Vending machine analogy. A function is a vending machine. You put in a code (spacing(16)) and out comes one item (16px). A mixin is more like a bakery rack that hands you a whole tray of items at once.

spacing() — the spacing scale

styles/abstracts/_spacing.scss (excerpt)
$spacing-values: (
  0: 0,
  4: 4px,
  8: 8px,
  12: 12px,
  16: 16px,
  24: 24px,
  32: 32px,
  48: 48px,
  /* ...many more keys... */
);

@function spacing($sizes...) {
  $result: ();

  @each $size in $sizes {
    @if not map.has-key($spacing-values, $size) {
      @error "Invalid spacing size: #{$size}. Available sizes: #{map.keys($spacing-values)}";
    }

    $result: list.append($result, map.get($spacing-values, $size));
  }

  @return $result;
}

Line by line

  1. $spacing-values is a map — Sass's name for a lookup table. Keys are integers, values are pixel sizes.
  2. @function spacing($sizes...) — declares a function. The ... means "accept any number of arguments and bundle them into a list called $sizes". So you can call spacing(8) or spacing(8, 16, 8, 16).
  3. The @each loop walks through every requested size.
  4. @if not map.has-key(...) — if you pass a size that is not in the map, Sass throws a build error that tells you exactly which keys are valid. This is the function's main job: validation.
  5. @return $result; — returns the looked-up pixel values. A single call like spacing(16) returns 16px. A multi-call like spacing(8, 16) returns the list 8px 16px — perfect for shorthand declarations like padding: spacing(8, 16);.
Why use spacing(16) instead of writing 16px? Three reasons: (1) the function fails loudly if you pick a non-system value, which prevents the codebase from drifting into random pixel numbers; (2) it is greppable — searching the codebase for spacing( finds every spacing decision at once; (3) the spacing scale could one day switch from pixels to rem; you would change it in one place and every call site would update automatically.

Other functions you will see

Function What it returns Example
spacing($key) A pixel value from the spacing scale. padding: spacing(24);
breakpoint($key) A pixel value from the breakpoint scale ("xs", "sm", "md", "lg", "xl", etc.). @media (min-width: breakpoint("md")) { ... }
font-size($key) A pixel value from the font-size scale. font-size: font-size(24);
line-height($key) A unitless line-height from the named scale. line-height: line-height(lh_3);
font-weight($key) A weight: bold, semi-bold, regular. font-weight: font-weight(semi-bold);
theme-color($key) A colour from the theme palette in _tools.color-palette.scss. color: theme-color("deep-teal");
type-size($key, $viewport) The desktop or mobile font-size from the type scale. Used internally by type-style.

8. Component APIs: Shared UI Primitives

The components/ folder holds UI primitives — small, focused mixin libraries that several sections share. A component file does not own Shopify section selectors. It exposes building blocks that section files combine inside the selectors they already own.

Lego analogy. A component file is a box of Lego pieces (mixins). A section file is the finished spaceship — it picks which pieces to use. The spaceship belongs to the section; the bricks belong to the box.

The eight component files

button

Foundational button styling primitives.

form-controls

Building blocks for inputs: control-surface, control-frame, control-padding, control-disabled, control-focus-reset, control-min-height.

text-primitives

Three typography mixins: mulish-body, hubot-text, nunito-heading. Each takes $color, $font-size, $font-weight, $line-height.

product-form

Cart-button and body-text mixins shared by product purchase UI.

product-price

regular-item and sale-item($color) for price displays.

product-rating

summary($border-color) and count for review-stars UI.

product-variants

option-label(...) for swatch and option label styling.

quantity

control, button, input for the +/− quantity widget shared by product and cart.

How a section uses a component

sections/_main-product.scss (top)
@use "../abstracts" as *;
@use "../components/product-form";
@use "../components/form-controls";
@use "../components/quantity";

.product__buy-button {
  @include form-controls.control-frame(100%, null, $control-height-product, $control-height-product);
  @include form-controls.control-padding(0, spacing(14));
}

Line by line

  1. @use "../abstracts" as *; — load tokens and core mixins globally for this file.
  2. @use "../components/product-form"; — load the product-form module with its default namespace (product-form.). Same for form-controls and quantity.
  3. .product__buy-button — the selector. It is owned by the main-product section, not by form-controls.
  4. @include form-controls.control-frame(100%, null, ...) — picks the control-frame mixin from the form-controls module. The four positional arguments map to $width, $max-width, $height, $min-height.
  5. $control-height-product is a token from abstracts/_tokens.scss. It resolves to 62px.
  6. @include form-controls.control-padding(0, spacing(14)); — vertical padding 0, horizontal padding 14px (looked up from the spacing map).
  7. Why namespace? Six months from now, a reviewer scanning the file instantly knows that control-frame lives in the form-controls module. With as *, they would have to search the codebase to find it.

9. Utilities: Tiny Classes Liquid Can Use Directly

A utility class is a small, single-purpose class designed to be written straight into Liquid markup. They are boring on purpose. A good utility does one thing and stays the same forever.

Drawer-of-pins analogy. Utilities are the drawer of safety pins, paper clips, and sticky notes. Any outfit can borrow one. You don't redesign the safety pin every season.

What is in utilities/

FileUtility classes
_visibility.scss .sr-only, .sr-only-focusable, .no-outline, the responsive .hide-* / .show-* pairs.
_text.scss .text-left, .text-center, .text-right, .text-upper, .text-lower, .text-bold, .truncate, .line-clamp-2, .line-clamp-3, .focus-ring, .fw-600, .fw-700, plus type-scale presets .small-text-bold, .styled-text, .badge-text.
_flex.scss All the flex modifiers (.d-flex, .justify-*, .items-*, etc.) plus opinionated layout shortcuts .stack-8/12/16/24 and .cluster-8/12/16/24.
_spacing.scss Margin and padding utilities generated from the spacing scale.
_layout.scss Container shortcuts, section padding shortcuts.
_color.scss Color utility classes built from the theme palette.

Good vs poor utility use

Good

snippet.liquid

Accessible hidden labels are reused across many snippets. .sr-only is the canonical utility for it.

Poor

section.liquid
<div class="summer-sale-product-heading-special">

Campaign-specific styling is not a "utility". It owns one piece of UI. Put it in the section file that owns the campaign block.

10. Breakpoints: Responsive Layouts The Right Way

The theme has a fixed set of named breakpoints. Use the named keys — never random pixel numbers — so the whole storefront breaks at the same widths.

Three ways to write a breakpoint

option A — function
.grid {
  @media (min-width: breakpoint("md")) {
    grid-template-columns: repeat(3, 1fr);
  }
}
option B — mixin (preferred)
.grid {
  @include up("md") {
    grid-template-columns: repeat(3, 1fr);
  }
}

Line by line

  1. @include up("md") { ... } — calls the up mixin with a content block. The mixin internally writes @media (min-width: 1025px) (it adds 1px to the breakpoint value to avoid a 1px gap with down).
  2. The block inside the curly braces is passed to the mixin via Sass's @content rule. The mixin places it inside the media query.
  3. Result: a media query that fires at and above the md breakpoint.
Available breakpoint mixins: @include up($key) (min-width), @include down($key) (max-width), @include min-width($key) (alias of up), @include max-width($key) (alias of down), @include between($min, $max) for a range.

Do Not: Random pixel numbers

bad.scss
@media (min-width: 873px) {
  .grid { grid-template-columns: repeat(3, 1fr); }
}

873px doesn't match any breakpoint in the system. Other sections will break at different widths and the storefront will look jittery on tablets.

Do: System breakpoints

better.scss
@include up("md") {
  .grid { grid-template-columns: repeat(3, 1fr); }
}

Now this section breaks at the same width as every other section.

Do And Do Not

11. Do / Don't: Patterns To Memorise

Pattern 1 — Deep nesting

Do Not

bad.scss
.collection {
  .grid {
    .product-card {
      .product-card__title {
        margin: 0;
      }
    }
  }
}

Compiled selector: .collection .grid .product-card .product-card__title. Four-deep specificity, hard to override, slow to read.

Do

good.scss
.product-card {
  @include stack(spacing(12));
}

.product-card__title {
  margin: 0;
}

Flat selectors. BEM-style class names already carry the meaning.

Pattern 2 — Hiding a single declaration behind a mixin

Do Not

bad.scss
@mixin red-text {
  color: red;
}

One declaration. Wrapping it in a mixin adds noise without removing any repetition.

Do

good.scss
@mixin control-frame($width, $max-width, $height, $min-height) {
  width: $width;
  max-width: $max-width;
  height: $height;
  min-height: $min-height;
}

Captures a real, repeated, multi-declaration pattern.

Pattern 3 — as * on every import

Do Not

bad.scss
@use "../components/form-controls" as *;
@use "../components/text-primitives" as *;

.field { @include control-frame(...); }

The call site no longer says which module owns control-frame. Eventually two modules will define the same mixin name and the compiler will complain.

Do

good.scss
@use "../components/form-controls";

.field { @include form-controls.control-frame(...); }

The call site states the ownership.

Pattern 4 — Section selectors in abstracts/

Do Not

abstracts/_mixins.scss
.main-product-info .product__title {
  margin-bottom: 12px;
}

Abstracts must not emit theme selectors. A reviewer expects abstracts to be silent until included.

Do

sections/_main-product.scss
.main-product-info .product__title {
  margin-bottom: spacing(12);
}

The section owns the selector. The shared value still comes from the system.

Pattern 5 — Campaign-specific utilities

Do Not

utilities/_campaign.scss
.black-friday-home-hero-title-large {
  font-size: 56px;
}

Campaign-named classes are not reusable. They are one section's styling masquerading as a utility.

Do

sections/_hero-banner.scss
.hero-banner__title {
  font-size: 56px;
}

The section owns it. If the campaign ends, you delete it in one place.

Pattern 6 — Raw transition values

Do Not

bad.scss
.link {
  transition: color 0.2s ease;
}

Hard-codes the timing. If we ever change the system speed, this file is out of sync.

Do

good.scss
.link {
  @include transition-config(color, $transition-duration-fast);
}

Uses the system timing tokens.

Pattern 7 — Huge mixins everywhere

Do Not

bad.scss
.a { @include full-card-system; }
.b { @include full-card-system; }
.c { @include full-card-system; }

If full-card-system contains 30 declarations and you include it 20 times, the compiled CSS contains 600 declarations. Mixins copy; they do not extend.

Do

good.scss
.card {
  @include card-surface(#fff, $radius-md, spacing(16));
}

Small focused mixins. Use one shared class instead of stamping the same big mixin onto 20 selectors.

Build Quality

12. Build Workflow: Compile, Diff, QA

SCSS changes nothing about the storefront until they are compiled. The build commands live in package.json and gulpfile.js. The standard rhythm:

terminal
npm run build:css
npm run verify:css
npm run build:js

Line by line

  1. npm run build:css — compiles all .scss files under styles/ into assets/main.css and assets/main.min.css. Also emits a source map.
  2. npm run verify:css — runs lint/format checks on the compiled output.
  3. npm run build:js — compiles JS assets. Run if you touched any JS or it was needed for the change.
  4. Always inspect the assets/main.css diff with git diff before pushing. The diff tells you exactly what the storefront will receive.

What kind of change did you make?

Source-only refactor

You re-organised SCSS but did not change behaviour. The assets/main.css diff should be empty (except possibly source-map noise). If output changed, investigate before continuing.

New utility class

The diff should show only the new class's declarations. No existing selectors should change.

Mixin signature change

The diff may cover many selectors that include the mixin. Inspect every call site. Update docs.

Visual behavior change

The diff is intentional. Run visual QA on the storefront pages this affects. Capture before/after screenshots if the change is subtle.

Debugging

13. Debugging: Common Errors And Their Fixes

Most Sass errors in this codebase come from one of four causes. Diagnose by reading the error first; do not guess.

Cause 1 — Namespace not loaded

Symptom

error
Error: There is no module with the namespace
"form-controls".
  ╷
3 │   @include form-controls.control-frame(...);
  │   ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
  ╵

You used form-controls.something but never wrote @use "../components/form-controls"; in this file.

Fix

good.scss
@use "../components/form-controls";

.field {
  @include form-controls.control-frame(...);
}

Add the @use at the top. Each file needs its own imports — module scope is per-file.

Cause 2 — Invalid spacing/breakpoint key

error
Error: Invalid spacing size: 17.5. Available sizes:
0, 1, 2, 3, ... 250

What happened

  1. You called spacing(17.5). The spacing map only has integer keys.
  2. The function's @error rule listed every valid key. Pick the closest one — usually 16 or 18 — and move on.
  3. If you genuinely need a non-system value, ask: is this really a one-off? If yes, write the literal pixel value with a comment explaining why. If no, add it to the spacing map.

Cause 3 — Wrong argument count or order

error
Error: Missing argument $min-height.

The mixin requires four arguments in a specific order (control-frame($width, $max-width, $height, $min-height)). Either pass all four, pass null for ones you do not need, or switch to named arguments.

Cause 4 — Selector moved to the wrong layer

If the storefront suddenly looks wrong after a refactor, check whether you moved a selector across folders. A selector that travels from sections/ to utilities/ now appears later in the compiled CSS — and a later same-specificity selector wins the cascade. Move it back.

Words you will read in PR reviews

        

          

            @use
            Loads a Sass module so this file can call its variables, functions, and mixins. Per-file scope.
          

          

            @forward
            Re-exports a module through a folder's _index.scss so consumers can @use the
            folder.
          

          

            @include
            Runs a mixin and copies its declarations into the compiled CSS at the include site.
          

          

            @mixin
            Defines a reusable group of CSS declarations with optional arguments.
          

          

            @function
            Defines a reusable computation that returns a single value (no CSS emitted).
          

          

            !default
            Flag on a variable: set this value only if it has not already been set. Used for design tokens.
          

          

            namespace
            The prefix that comes from @use "module" — e.g. form-controls.control-frame.
            Disabled by as *.
          

          

            token
            A named Sass variable for a design decision (control height, ring width, transition speed). Names
            describe roles, not values.
          

          

            utility
            A tiny class meant to be applied directly in Liquid. Single-purpose, reusable, boring.
          

          

            source-only refactor
            A change that improves the SCSS source without altering the compiled CSS. Verify with a clean
            assets/main.css diff.
          

          

            cascade
            The order in which CSS rules apply. Later same-specificity rules win. Folder order in main.scss
            controls cascade order.
          

          

            compiled CSS
            The output the storefront serves — assets/main.css / assets/main.min.css. The
            only thing the browser sees.
          

        


        
Folder cheat sheet

        

          

            
Use abstracts/ for

            
Tokens, scales, breakpoint helpers, generic mixins — anything output-free.

          

          

            
Use components/ for

            
Reusable UI primitives (mixin libraries): buttons, form controls, text, price, rating, variants,
              quantity.

          

          

            
Use sections/ for

            
Selectors owned by one Shopify section.

          

          

            
Use templates/ for

            
Selectors tied to one Shopify template page (cart, etc.).

          

          

            
Use layout/ for

            
Large structural pieces present on most pages: header, footer.

Tiny, reusable, markup-facing classes Liquid can apply directly.
